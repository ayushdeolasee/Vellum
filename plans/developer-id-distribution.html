Developer ID Distribution

What has to change for Vellum/macOS to ship as a signed, notarized DMG.

Manual release checklist. Scope: outside the Mac App Store.

Goal

A .dmg that a stranger can download, drag to /Applications, and open through the normal macOS first-launch confirmation without an unidentified-developer block. Vellum must use a Developer ID Application certificate and Hardened Runtime; the final disk image must be signed, notarized, and stapled.

1. Hard blockers

The paid-team certificate is the only account-level blocker. Hardened Runtime and the Developer ID export configuration are already prepared on this branch.

1.1 Hardened Runtime prepared

The Vellum target sets ENABLE_HARDENED_RUNTIME: "YES". Apple's notary service rejects submissions without it.

Hardened Runtime is a set of kernel-enforced restrictions baked into the code signature: other processes cannot inject code into the app, DYLD_* environment overrides are ignored, library validation restricts loading to libraries signed by the same team or by Apple, and debugger attachment is refused unless explicitly allowed. Because it changes runtime behaviour, enabling it can surface crashes that never happened in development.

Risk areas to exercise once enabled: the WKWebView surfaces (WebKit's JIT lives in Apple's own signed XPC process, so this is normally fine), the OAuth loopback listener in Vellum/Services/Ai/OAuth/, PDFKit page-text extraction and Live Text, and anything that reads the bundled JS in Vellum/Resources/.

1.2 Wrong certificate type blocker

CODE_SIGN_IDENTITY: "Apple Development" is a development-only certificate. Gatekeeper on any machine other than a registered development device will refuse to launch it. Distribution outside the App Store requires a Developer ID Application certificate, which only a paid Apple Developer Program membership can issue.

Developer ID Installer is a separate certificate for .pkg installers and is not needed for DMG distribution.

Keep normal builds on Apple Development. On certificate day, select the paid team in Xcode; xcodebuild -exportArchive uses Distribution/ExportOptions.plist to export the archive with the installed Developer ID identity.

Verify before enrolling

After the paid membership activates, make DEVELOPMENT_TEAM match that team and create the Developer ID certificate under the same account.

No provisioning profile is required for Developer ID signing so long as the app uses no profile-backed capability (iCloud, App Groups, Push). Vellum/macOS currently uses none.

1.3 Entitlements none needed

Vellum does not need a signing-entitlements file for direct distribution. Add a Hardened Runtime exception only if runtime testing proves that a specific feature requires one.

Do not add

No iCloud container entitlement. The macOS app deliberately writes into the user-visible CloudDocs directory rather than an app ubiquity container (see Vellum/Services/Web/WebStorage.swift), which works because the app is unsandboxed. Adding an iCloud entitlement is a storage migration, not a signing change, and belongs to #149.

2. Doable before the certificate

Hardened Runtime can be tested now with the existing Apple Development certificate. The runtime restrictions are the same; only the distribution trust chain is missing.

xcodebuild -project Vellum.xcodeproj -scheme Vellum \
  -configuration Release -destination 'generic/platform=macOS' \
  -derivedDataPath build/DerivedData build

codesign -dv --verbose=4 \
  build/DerivedData/Build/Products/Release/Vellum.app
# Expected in the signature flags: runtime

2.1 App Sandbox — decide and record

ENABLE_APP_SANDBOX: "NO" is correct and should stay. Notarization does not require sandboxing; only the App Store does. Enabling it would break the CloudDocs storage path and the document-library access model. The decision should be written down so it is not "fixed" later by someone assuming sandboxing is always desirable.

2.2 Info.plist cleanups

In Vellum/Resources/Info.plist:

KeyCurrentChange
NSAppTransportSecurity → NSAllowsArbitraryLoads true Permitted outside the App Store, but it disables App Transport Security process-wide. If it exists only for the local OAuth loopback, narrow it to NSAllowsLocalNetworking.
NSHumanReadableCopyright empty string Fill in — it is shown in the About window of a shipping app.
LSApplicationCategoryType absent Not required for DMG distribution; add anyway for Finder and Launchpad metadata.
MARKETING_VERSION / CURRENT_PROJECT_VERSION 0.1.0 / 1 Settle real release numbering. CFBundleVersion must strictly increase across releases or the update check misjudges which build is newer.

2.3 Application icon

CFBundleIconFile points at Vellum/Resources/AppIcon.icns, which is what actually ships. Separately, an untracked Icon Composer document sits at Vellum/Untitled.icon with a placeholder name. Decide which is authoritative, name it properly, commit it, and confirm every required size including 1024 pt renders. A placeholder icon is the first thing a downloader sees.

2.4 Scrub the public repo of personal identifiers privacy

This repository is public. The comment block above the signing settings in project.yml embeds personal email addresses and Apple Developer Team IDs in cleartext. They are already in the published git history, so removing them now limits future exposure rather than undoing it.

  • Rewrite the comment to explain the reasoning (stable signing identity keeps TCC folder-access grants from resetting on every rebuild) without naming accounts.
  • Keep the Team ID out of the tracked file where practical — an untracked .xcconfig or a CI/local environment variable feeding DEVELOPMENT_TEAM.
  • Never commit the notarization credentials: the App Store Connect issuer ID, key ID, or .p8 private key. Add the key's path pattern to .gitignore before the certificate arrives.

2.5 Keep the first release manual

Use the commands in §4. They intentionally avoid CI, third-party DMG tools, and automatic update installation.

3. Certificate day

If §2 is complete, this reduces to a short, mechanical sequence:

  1. Enrol the paid membership under the confirmed Apple ID; note the Team ID.
  2. Create a Developer ID Application certificate and install it in the login keychain.
  3. Point DEVELOPMENT_TEAM at the paid Team ID, then run xcodegen generate.
  4. Store notarization credentials with xcrun notarytool store-credentials VellumNotary --apple-id "<apple-id>" --team-id "<team-id>". The password is entered at a secure prompt and saved in Keychain.
  5. Run §4 and test the downloaded DMG on another Mac.

4. Manual release commands

Run from the repository root after the paid team and Developer ID Application certificate are installed:

RELEASE_DIR="$PWD/build/release-$(date +%Y%m%d-%H%M%S)"
mkdir "$RELEASE_DIR"

xcodebuild archive \
  -project Vellum.xcodeproj \
  -scheme Vellum \
  -configuration Release \
  -destination 'generic/platform=macOS' \
  -archivePath "$RELEASE_DIR/Vellum.xcarchive"

xcodebuild -exportArchive \
  -archivePath "$RELEASE_DIR/Vellum.xcarchive" \
  -exportOptionsPlist Distribution/ExportOptions.plist \
  -exportPath "$RELEASE_DIR/export" \
  -allowProvisioningUpdates

mkdir "$RELEASE_DIR/dmg-root"
ditto "$RELEASE_DIR/export/Vellum.app" \
  "$RELEASE_DIR/dmg-root/Vellum.app"
ln -s /Applications "$RELEASE_DIR/dmg-root/Applications"

diskutil image create from \
  --volumeName Vellum \
  --format UDZO \
  "$RELEASE_DIR/dmg-root" \
  "$RELEASE_DIR/Vellum.dmg"

codesign --force \
  --sign "Developer ID Application: <name> (<team-id>)" \
  --timestamp \
  --identifier com.vellum.app.dmg \
  "$RELEASE_DIR/Vellum.dmg"

xcrun notarytool submit "$RELEASE_DIR/Vellum.dmg" \
  --keychain-profile VellumNotary \
  --wait

xcrun stapler staple "$RELEASE_DIR/Vellum.dmg"
  • Staple means embedding the notarization ticket into the file so Gatekeeper can validate it without a network round-trip. Only the outer DMG is submitted and stapled.
  • Notarization is asynchronous; --wait blocks until Apple returns a verdict. On rejection, xcrun notarytool log <submission-id> returns a JSON breakdown of every offending binary.
  • Keep build/ out of the repo — it is already gitignored.

4.1 Distribution channel already assumes GitHub Releases

Vellum/App/UpdateChecker.swift fetches a manifest from releases/latest/download/latest.json and its install() simply opens the releases page. So the channel is decided; what is missing is publishing that latest.json alongside each DMG, with a schema matching what the checker decodes.

Do not extend without signing

The manifest is fetched over TLS but is otherwise unauthenticated. That is acceptable while install() only opens a browser. If it is ever changed to download and install a payload automatically, it needs signature verification on the manifest first — or adopt Sparkle, which solves this with EdDSA-signed appcasts.

5. One-time fallout

Moving from an Apple Development identity to Developer ID Application changes the app's code signing identity. macOS keys several per-app grants to that identity, so a one-time reset is unavoidable and should be planned rather than discovered:

  • TCC permissions reset. Documents, Desktop, and Downloads access is granted against the signing identity. Every user — including on the development machine — re-prompts once. This is the same mechanism the existing project.yml comment describes.
  • Keychain items become inaccessible. Items written by Vellum/Services/KeychainStore.swift carry an access control list bound to the old identity's designated requirement. Stored AI provider keys and OAuth tokens will need re-entering once. Either add a graceful "your saved key needs re-entering" path, or accept it and say so in the release notes — but do not let it surface as an opaque auth failure.

Do this changeover once, deliberately, and do not flip identities again afterwards.

6. Out of scope

  • Mac App Store. Would require App Sandbox, which breaks the current storage model. Not planned.
  • App Sandbox. Stays off — see §2.1.
  • iCloud entitlements and container migration. Owned by #149; unrelated to Gatekeeper or notarization.
  • iPad and iPhone branches. This checklist covers the macOS app only.
  • Sparkle / auto-update. A real decision, but a separate piece of work with its own key management.

7. Verification

A build is not shippable until all of these pass:

# Set this to the timestamped directory created in §4.
RELEASE_DIR="$PWD/build/release-<timestamp>"

# signature is Developer ID, hardened runtime flag present
codesign -dv --verbose=4 "$RELEASE_DIR/export/Vellum.app"

# every nested binary is signed and sealed
codesign --verify --deep --strict --verbose=2 \
  "$RELEASE_DIR/export/Vellum.app"

# Gatekeeper accepts the disk image as notarized
spctl -a -vvv -t open \
  --context context:primary-signature \
  "$RELEASE_DIR/Vellum.dmg"
#   expected: source=Notarized Developer ID

# the ticket is actually attached
xcrun stapler validate "$RELEASE_DIR/Vellum.dmg"

Then download the DMG on a Mac that has never run Vellum, drag to /Applications, and double-click. The normal first-launch confirmation is expected; an unidentified-developer block is not. Confirm the quarantine attribute is present first (xattr -p com.apple.quarantine) because local copies can produce a false pass.
