1 · Executive summary

Both services are integrable through official, documented APIs, with a shared read-only architecture:

  • Readwise Reader uses a simple personal access token: the user copies a token from the service's website and pastes it into Vellum. No OAuth dance is required.
  • Raindrop supports full OAuth 2, but without PKCE and requiring a client secret — awkward for a native app. It also offers a no-expiry "test token" the user can copy from their own Raindrop settings. v1 ships the token-paste path for both services (one uniform UX), with real OAuth for Raindrop as a later upgrade.
  • Every service returns the original source URL for each saved item — which is exactly what Vellum wants, because Vellum renders the original page itself in its own web viewer. An external article "opens in Vellum" by simply feeding that URL into the existing appStore.openUrl(_:) pipeline. Zero new rendering code.
  • PDFs: Readwise can hand us the original PDF binary (withRawSourceUrl); Raindrop file-raindrops have a direct download link. Vellum downloads those into a managed folder and opens them through the normal PDF pipeline.

The integration is read-only in v1: browse your external library, search it, open items. Writing back (archiving, progress sync, save-from-Vellum) is a later phase.

Key decision

External items are browsed live, not imported. Vellum keeps a lightweight cached index of each service's library (title, URL, tags, etc. — no page content) so the list is instant and works offline, but an item only becomes a "real" Vellum document the moment you open it — at which point it flows through the exact same machinery as a pasted URL or opened PDF, gaining annotations, AI chat, scratchpad, and offline saving for free.

Concept — token auth vs. OAuth

A personal access token is just a long random string the service generates for you; whoever holds it acts as your account. The user copies it once from the service's website and the app stores it. OAuth 2 instead has the app redirect the user to the service's login page in a browser; after approval the service hands the app short-lived tokens. OAuth is better UX for mass-market apps (no copy-pasting), but Raindrop's flavor requires a client secret — a credential that identifies the app, which can't be kept secret inside a distributed binary. The standard fix, PKCE, isn't supported by Raindrop. Options if/when we want real OAuth: embed the secret anyway (common indie-app practice — the secret guards nothing valuable here since users only access their own data), or run a tiny token-exchange proxy (e.g. on hermes). Deferred to a later phase; token-paste ships first.

Two surfaces change: Settings (connecting accounts) and the Welcome screen (browsing external libraries). Nothing changes in the document viewer — once opened, an external item is an ordinary Vellum tab.

macOS gotcha (from project memory)

The token field must use the existing RevealableSecureField, not a bare SecureField — bare secure fields plus any popover trigger the macOS 27 Passwords-autofill ViewBridge crash already documented in this repo.

4 · User workflow: connecting each service

Readwise Reader — ~30 seconds

  1. Settings → Integrations → Connect… on the Readwise card.
  2. Sheet's button opens readwise.io/access_token in the browser (user may need to log in to Readwise there).
  3. Copy token → paste in Vellum → Connect.
  4. Vellum validates via GET /api/v2/auth/ (expects 204), stores the token in Keychain, starts the initial sync. The Readwise segment appears on the Welcome screen with a progress indicator until the first page of items lands (seconds), filling in behind the scenes.

Raindrop.io — ~1 minute

  1. Settings → Integrations → Connect… on the Raindrop card.
  2. Sheet explains the one extra step: open app.raindrop.io/settings/integrations → For Developers → create an app (any name) → copy its Test token. The sheet walks this with numbered steps and a screenshot-style hint, since it's the less obvious of the two.
  3. Paste → validate via GET /rest/v1/user → Keychain → initial sync (collections list first, then items).

Test tokens don't expire, which is why this is viable as more than a stopgap. When the app is distributed more widely, phase 4 replaces this with true OAuth through the existing loopback-server infrastructure and this sheet becomes a single "Sign in with Raindrop" button.

Disconnecting

One click, with a confirm. Deletes the Keychain entry and the cached index. Downloaded PDFs are kept (they may have annotations) — noted in the confirm dialog with an optional "also delete downloaded files" checkbox.

5.1 The unified item model

Each client maps its service's response into one normalized struct, so the UI and cache never care which service an item came from:

enum ReadLaterProvider: String, Codable, CaseIterable { case readwise, raindrop }

struct ReadLaterItem: Codable, Identifiable, Hashable, Sendable {
    var id: String                  // "<provider>:<service item id>"
    var provider: ReadLaterProvider
    var title: String
    var author: String?
    var sourceURL: URL              // the original page — what Vellum opens
    var kind: Kind                  // .article, .pdf, .epub, .video, .other
    var excerpt: String?
    var imageURL: URL?              // cover/thumbnail (loaded lazily in rows)
    var tags: [String]
    var group: String?              // Readwise location / Raindrop collection id
    var savedAt: Date
    var updatedAt: Date             // drives incremental sync + sorting
    var pdfDownload: PDFSource?     // how to fetch the binary, if it's a file item
}

group is deliberately a flat string + a separate per-provider ReadLaterCollection list (id, title, parent) — enough to render Raindrop's nested collections and Readwise's locations without introducing a full folder taxonomy into Vellum's own library model, which currently has none.

5.2 The client protocol

protocol ReadLaterClient: Sendable {
    var provider: ReadLaterProvider { get }
    func validate(token: String) async throws -> AccountInfo   // name/email for the settings card
    func collections(token: String) async throws -> [ReadLaterCollection]
    func items(token: String, since: Date?, cursor: String?) async throws -> ItemPage
    func pdfDownloadURL(token: String, itemID: String) async throws -> URL  // Readwise: re-fetch w/ withRawSourceUrl
}

Implementation style copies the existing AI clients (OpenAIClient et al.): plain URLSession.shared.data(for:), tolerant Codable decoding (every field the vendor might drop is optional — Raindrop's docs explicitly warn fields appear/disappear). Shared plumbing in ReadLaterClient.swift handles the one behavior both vendors share: 429 → read Retry-After → sleep → retry (max 3), plus mapping 401/403 to a typed .tokenRejected error so the UI can say something useful.

5.3 Credentials

Extend the existing KeychainStore with account constants for readwise and raindrop. Tokens never touch UserDefaults or the JSON cache. Non-secret connection metadata (last sync date, item count, account display name) lives in UserDefaults under integrations.<provider>.*.

Concept — why Keychain

UserDefaults is a plaintext plist on disk, readable by anything running as your user, and it gets swept into backups. The macOS Keychain encrypts entries at rest and gates access to the app that stored them. Anything that grants account access — API tokens included — belongs there. Vellum already does this for AI keys, so this is just two more rows in an existing table.

5.4 Concurrency shape

IntegrationsSyncEngine is an actor — all network calls and cache-file writes happen inside it, never on the main actor. This follows the hard-won project rule from the session-backends work: main-actor file I/O caused freezes before; don't reintroduce it. The flow:

UI (@MainActor)                      Background
──────────────                       ──────────
IntegrationsStore  ──syncNow()──▶  IntegrationsSyncEngine (actor)
  @Observable                         │  fetch pages, honor rate limits
  items, states,                      │  merge into IntegrationsCache (JSON on disk)
  filters                             ▼
        ◀────await MainActor: store.apply(snapshot)──┘

The store publishes immutable snapshots ([ReadLaterItem] per provider); SwiftUI diffing handles the rest. Search/filtering is a pure in-memory operation over the snapshot — no database needed at these sizes (even 10k items of metadata is ~a few MB).

5.5 Cache on disk

~/Library/Application Support/com.vellum.app/integrations/
├── readwise/ index.json   syncstate.json
├── raindrop/ index.json   syncstate.json   collections.json
└── downloads/<provider>/<itemid>.pdf
  • index.json — the full normalized item list, written atomically (temp file + rename, same pattern as WebLibrary).
  • syncstate.json — the incremental-sync watermark (updatedAfter / updated_since / Raindrop high-water lastUpdate) and any in-flight cursor so an interrupted initial sync resumes instead of restarting.
  • Deliberately local, not in the iCloud/custom web-library storage location: this is a re-fetchable cache derived from the services, not user data — syncing it would create cross-device merge questions for zero benefit. Downloaded PDFs also stay local in v1; once opened they're ordinary file-path documents and behave like any other PDF the user has (annotations embed in the file). Revisit if it feels wrong in use — flagged as an open question in §8.

6 · Sync engine details

Triggers

  • Initial sync — on connect: fetch collections (Raindrop), then walk the full item list page-by-page, writing each page into the cache so the UI populates progressively.
  • Delta sync — on app launch, when the user switches to a service's tab (if > 5 min stale), on manual Sync Now, and on a 30-min timer while running (toggleable in Settings).

Per-service strategy

ServiceInitial syncDelta syncDeletions
Readwise/v3/list/ pages of 100. At 20 req/min, a 5,000-item library ≈ 50 requests ≈ 2.5 min — hence progressive fill + resumable cursor, never a blocking spinner.updatedAfter=<watermark>; cheap, usually 1 request.Deltas don't report deletions. Weekly (and on manual Sync Now) run a full re-walk in the background and drop cached items the walk didn't see. Cheap at these rate limits; correctness without vendor support.
Raindrop/raindrops/0 pages of 50, 120 req/min — even huge libraries sync in seconds. Collections tree first.No delta param: fetch sorted by -lastUpdate, stop at the first page whose items are all already-known-and-unchanged.
Concept — cursor pagination & watermarks

These APIs don't return everything at once; each response includes a cursor — an opaque bookmark you pass back to get the next page. A watermark is the highest updated_at you've seen: next sync you ask only for items changed after it, turning a 50-request full walk into a 1-request check. The one subtlety: record the watermark as of sync start, not sync end, so items updated mid-sync aren't skipped forever.

Failure behavior

  • Network down → keep serving the cache silently; retry next trigger. The Welcome screen shows a subtle "offline — showing cached list" note only if a manual sync fails.
  • 401/403 → flip the service to Needs attention (Settings card + library banner). Never auto-delete the cache on auth failure — the token might just need re-pasting.
  • 429 → handled inside the client (sleep + retry); the sync engine additionally spaces Readwise page requests ~3s apart to stay under 20/min by construction.

7 · Implementation phases

Each phase is independently shippable and PR-sized. Readwise goes first: simplest auth, best-documented API, and it exercises every subsystem (tokens, sync, browse UI, PDF download) so Raindrop becomes mostly "write a client + a mapper".

Phase 1 — Scaffolding + Readwise end-to-end

  • Models, client protocol, Keychain accounts, cache, sync-engine actor, IntegrationsStore.
  • Settings → Integrations tab with the Readwise card + connect sheet.
  • Welcome-screen source switcher + Readwise list with Location filter and search.
  • Open article → openUrl; open PDF → download via withRawSourceUrl → openFile.
  • Unit tests: response-fixture decoding, item mapping, watermark logic, 429 retry.

Phase 2 — Raindrop

  • RaindropClient (test-token auth), collections tree fetch + picker UI, file-raindrop downloads, the sorted-by-lastUpdate delta strategy.

Phase 3 — Polish

  • Cover-image thumbnails (lazy, disk-cached), deletion-sweep sync, progress toast for large downloads, empty states, auto-refresh timer + toggle, "Open Original in Browser" / "Copy Link" context items.

Phase 4 — Later / optional

  • Real OAuth for Raindrop (loopback server + PKCE infra already exists; needs the client-secret decision — embed vs. proxy on hermes).
  • Write-back: archive in Readwise from the context menu; push reading progress; "Save current page to …" from Vellum's toolbar where supported.
  • "Import into Vellum library" bulk action (turns external items into Saved offline archives).

9 · Verification plan

  • Unit tests (Swift Testing, run via xcodebuild CLI): fixture-based decode/mapping tests per client; watermark and dedupe logic; 429 retry with a stubbed URLProtocol.
  • Live API smoke tests: a small debug-only harness (or curl scripts in tools/) hitting each real API with your tokens — run once per phase, not in CI.
  • UI verification with codex-cli computer-use (per project convention — driven by Codex/Sonnet/Opus, never Fable): connect-sheet flow with a real token, source-switcher browsing, opening an article and a PDF end-to-end, token-error banner by deliberately revoking a token.
  • Multi-worktree hygiene: stage only integration files; regenerate the Xcode project from project.yml rather than committing pbxproj churn.
