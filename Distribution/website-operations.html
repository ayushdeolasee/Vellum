Analytics budget

ControlConfigured behavior
SchemaPublic POST accepts only event, version and build; event must be first_launch. Version/build contain 1–32 release characters. Body is at most 1,024 UTF-8 bytes, including streamed bodies.
Rate gateAll event writes, including download and appcast GETs, share one constant key. Binding allows approximately 60 attempts/minute per Cloudflare location. No IP, device or installation identifier is used. This is not a global request quota.
Daily row capOne atomic conditional insert permits at most 5,000 analytics rows per UTC day across all event types. POST returns 429 when capped; downloads and update responses still work. A missing/broken binding prevents analytics writes.
RetentionCron at 03:17 UTC daily deletes analytics older than three calendar months and waitlist rows older than twelve calendar months, including invited rows. No subsequent signup/event is needed. Normal scheduling adds up to one day to those cutoffs.

The numeric limits are provisional, not derived from live traffic. The daily cap limits retained event rows, not all D1 billable writes: indexes and retention also cost writes. Each quota check looks up one indexed UTC-day counter; a database trigger updates that counter atomically with a successful insert. Capped requests do not write counters or events, but still perform the constant-size quota read. Daily counters are aggregates and are removed after three months. Worker invocations, invalid payload traffic, update proxy fetches, waitlist writes and D1 read quota are not globally capped here. These controls reduce analytics writes but do not establish a complete account spending ceiling. Unauthenticated counts can still be polluted or exhausted.

Before enabling this revision in production, the owner must record the Worker/D1 plan, existing WAF/bot/edge rate controls, the uniqueness of rate namespace 308 within the account, normal traffic, and an appropriate read/write/request budget. Do not assume edge settings are present.

Daily checks and alerts

The authenticated GET /api/analytics-health uses the existing export bearer token and returns only analyticsToday, analyticsBudgetToday, analyticsDailyLimit, analyticsOverdue and signupsOverdue. analyticsToday counts stored rows within today's UTC interval; analyticsBudgetToday is the counter controlling acceptance, and null means today's counter is missing. A 503 is a failed diagnostic, not zero usage. It never returns identities or event payloads. Fetch it with a private client that obtains the token from the established Keychain store; do not paste the token into shell history, reports or URLs. No new token or tracking key is required.

Check Cron Past Events after 03:17 UTC. Successful cleanup logs only aggregate deletion counts; a rejected database operation fails the scheduled handler rather than logging success. Overdue counts should clear after a successful run; newly expired rows between daily runs are expected. If a run is missed, verify the cron/binding and replay the deletion queries below, then verify the counts again. Record run time and aggregate counts only.

Configure and test notifications for Worker errors/usage and D1 rows read/written in the Cloudflare account before rollout. Use warning thresholds at 80% of the owner's approved account quotas/spending budget, accounting for all other workloads, and notify the owner on failed or missing daily cleanup. Cloudflare availability depends on the account plan. Neither alert settings nor delivery have been inspected or changed by this implementation. The health route is reporting, not an automated alert service.

Choose a grace period after 03:17 UTC and independently verify missing-completion alerts reach their intended recipient. Zero overdue rows alone do not prove cron ran. Omitted Wrangler observability settings do not prove live account logging is disabled. Failed background download/appcast analytics log only Unable to record aggregate analytics event, without request or database error details, while delivery can still succeed.

Migration backup, restore and counter reconciliation

  1. Pause writes, including download and appcast GET analytics, and drain pending requests. Retain a backup or recoverable restore point before schema/data changes. Backups and identity exports contain private waitlist information.
  2. Apply migrations in order. Migration 0004 seeds the current UTC day and adds the insert trigger. Reapplying its SQL preserves an existing counter and signup identities/statuses; it does not repair a stale counter. Verify both counter table and trigger before resuming traffic.
  3. If restoration is necessary, restore a coherent database including identities/statuses, events, counters, schema and trigger; retain the failed state. Apply only missing migrations, reconcile today's counter, then recheck private health before resuming writes. An older snapshot may lose later signups and consumed quota; preserve later data where possible and use a conservative counter if the consumed count is unknown.

With writes paused, raise a missing or undercounted counter to the stored row count without lowering a known consumed budget:

INSERT INTO analytics_daily_budget (day, event_count)
SELECT date('now'), COUNT(*) FROM analytics_events
WHERE created_at >= date('now') AND created_at < date('now', '+1 day')
ON CONFLICT(day) DO UPDATE
SET event_count = MAX(analytics_daily_budget.event_count, excluded.event_count);

Never delete today's counter while today's events remain. Deleting rows does not refund consumed quota. Keep a counter higher than the stored row count until UTC midnight unless a separately reviewed recovery establishes the actual consumed count. If that count is unknown, use at least 5,000 to close today's budget safely. Reapplying migration 0004 does not repair an existing undercount; reconcile and recheck health.

At UTC midnight the lookup selects the new day. Its first accepted event creates/increments that day's counter atomically. Yesterday's full quota does not block today; no manual reset is needed.

Retention recovery and early deletion

From Distribution/website, first run the following SQL against an isolated local database to verify the intended cutoff. Only after separately authorizing production maintenance should the owner run the same queries against the deployed D1 database. The scheduled job performs them in a D1 batch.

DELETE FROM analytics_events
WHERE created_at < datetime('now', '-3 months');
DELETE FROM testflight_signups
WHERE created_at < datetime('now', '-12 months');
DELETE FROM analytics_daily_budget
WHERE day < date('now', '-3 months');

When the beta ends or records are no longer needed for invitations, the owner must remove the applicable waitlist records earlier, as promised in the privacy policy. Individual deletion requests use an exact email match with a bound SQL parameter in a private database client. Do not place identities in logs or command history. Apple holds its own copy of information already imported to App Store Connect.

CSV identity handling

The authenticated export retains the existing First Name, Last Name, Email Address columns and UTF-8 encoding. Before independent CSV quoting, an apostrophe is added to formula-leading (=, +, -, @) cells, including prefixes hidden behind whitespace or control characters. Leading tab/CR/LF cells are also marked as text. Ordinary commas, quotes, newlines and Unicode values round-trip as CSV data without changing their content.

The apostrophe is intentional and may appear literally in a data-only importer. A formula-prefixed email gains a prefix and must not be treated as the original invitation address. Apple CSV import has not been exercised here; validate its current sample/template and harmless fixtures before uploading real records. For unusual prefixed identities, use the original record through a private database client and enter it directly into Apple's form, instead of stripping the guard and reopening the CSV in a spreadsheet. Do not resave protected CSV through a spreadsheet without rechecking cell prefixes.
