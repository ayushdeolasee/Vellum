## Reproduction and validation

The four Swift factories produce the checked-in bytes on every run. The encrypted and signed samples are fixed test inputs. Regenerating them introduces fresh encryption randomness or a new signing identity.

To recreate encryption, open the classic PDF with pikepdf and call `pdf.save(output, encryption=pikepdf.Encryption(owner="fixture-owner", user="vellum", R=6))`. For a new signature, use a throwaway directory and key, then run the following commands against the classic PDF.

```sh
openssl req -x509 -newkey rsa:2048 -sha256 -nodes -days 3650 \
  -subj '/CN=Vellum Fixture Signer' -keyout disposable.pem -out certificate.pem
pyhanko sign addsig --field FixtureSignature pemder --no-pass \
  --key disposable.pem --cert certificate.pem classic-two-column.pdf digitally-signed.pdf
rm disposable.pem
```

From the repository root, run `uv run tools/pdf-fixtures/validate.py` with Poppler and OpenSSL on PATH. It parses PDF objects with libqpdf recovery disabled, checks the detached signature against the actual byte ranges and samples the corner colors from all four rendered pages. `PdfFixturesSanityTests` compares the bundled bytes with the Swift factories and opens the fixtures in PDFKit on Apple platforms.

## Classic annotation exchange

`mac-annotation-source.pdf` is a synthetic macOS PDFKit export. A Quartz
612 × 792 page contains one gray bar. PDFKit set its crop to [24 36 576 744],
rotated it 90°, and added a native Text annotation named `mac-existing`.
The iPad source is the existing PencilKit export documented in
[INK-PROVENANCE.md](INK-PROVENANCE.md).

`PdfAnnotationIncrementTests.testAppleSourcesAndLinuxExchangeBytes` creates a
highlight and note and pins the highlight on each original. Running it in the
pinned arm64 Linux container with `VELLUM_ANNOTATION_FIXTURE_EXPORT` set to a
directory emits `linux-on-mac.pdf` and `linux-on-ipad.pdf`. Ordinary runs
compare the generated bytes with those exports.

The Mac hosted exchange passed its one selected test at `63c42b52`. The
iPad hosted run passed all seven selected tests (zero failures or skips) at
`0a8347defbff5d66bced63e26322ef44929873c0` on the arm64 iPad Pro 13-inch
(M5) simulator, iPadOS 26.5 (23F77). Both hosts opened both forward files.
On `linux-on-ipad.pdf`, the iPad exchange checked five annotations, the exact
original ink carrier string and marker, and decoded both strokes with PencilKit.

An independent Linux PDFium read of both files confirmed all three slot IDs

Both sticky icons grew from 18 × 18 to 24 × 24 PDF points in the iPad reply.
The Mac reply kept the original foreign ID and both anchors. The Linux forward
writer's separate offset and slot checks cover untouched original objects on
both inputs. The iPad return observation records a limitation of the Apple save
when a peer relies on the foreign ID or note position.

Annotation saves append revisions. Editing or deleting a note changes what
readers show, while its earlier text and rich content remain recoverable in
the file. This writer never compacts, rewrites, or securely erases that history.
The classic inspection limit is 64 revisions including the original. A
one-revision source can accept up to 63 increments within the other proof
limits. Further edits report the inspection limit and preserve the last save.

The portable display decoder recognizes PDFDocEncoding and the PDF 2.0 UTF-8
BOM. macOS CGPDF decoded the raw string `<EFBBBF616263>` as “ï»¿abc”
while the portable display decoder reads “abc”. A BOM-prefixed UTF-8 string
therefore cannot identify an annotation or witness a shared document ID.
An existing ambiguous stamp is preserved, and the shared file uses its byte hash.
